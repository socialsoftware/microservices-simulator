### Cross-artifact contradictions found

**C2-1 (Critical) — service dependency injection: constructor vs `@Autowired` field.**

`docs/concepts/service.md:35-44`:

> **Every dependency goes through the constructor. A service declares no `@Autowired` field.** All
> fields are `final` … a session appending a method that needs a collaborator the service does not yet
> hold widens the constructor **and** the matching `@Bean` method in `BeanConfigurationSagas.groovy`,
> whichever collaborator it is — there is no second, field-injected category that would let it skip the
> `@Bean` edit.

`.claude/skills/implement-aggregate/session-b.md:208-212`:

> That list is split two ways, and the bean method must match the split: `UnitOfWorkService`, the
> repository and the custom repository are **constructor** parameters, while the factory and
> `AggregateIdGeneratorService` are `@Autowired` **fields** on the service and therefore do not appear
> in the bean method at all. Passing all five to the constructor does not compile against the service
> `docs/concepts/service.md` prescribes.

The final sentence asserts the doc prescribes the split; the doc prescribes the opposite. The
`@Bean` snippet at `session-b.md:215-220` omits the factory accordingly. `session-c.md:313-318`
restates the doc's rule correctly:

> A service takes every dependency through its constructor and declares no `@Autowired` field
> (`docs/concepts/service.md` § Injected Dependencies), so a write method needing a collaborator the
> service does not yet hold requires **two** edits, not one.

Two skills prescribe opposite things for the same file, and one of them misattributes its rule to the
doc. **Critical**: session `b` creates the service and its `@Bean` method, so the wrong shape is
established for the whole aggregate and session `c` then appends against a contradictory rule.

**C2-2 (Major) — which session writes the `create{Aggregate}` fixture helper.**

`classify-and-plan/SKILL.md:562-564`:

> Session `a` appends one error-message constant per P1 rule and a `create{Aggregate}(...)` fixture

`session-b.md:257` confirms session `b` owns it. The plan-generation skill's annotation on the 2.N.a
row therefore attributes to session `a` a file edit session `a` is explicitly forbidden to make.

**C2-3 (Major) — event class filename under the shared `{Event}` substitution.**

`classify-and-plan/SKILL.md:684-687` defines:

> `{Event}` → event name **without** the "Event" suffix (e.g., "UpdateWarehouseName" for
> "UpdateWarehouseNameEvent"). It is used bare only inside
> `notification/subscribe/{Aggregate}Subscribes{Event}.java`; the event class itself is
> `events/{Event}Event.java`, which restores the suffix.

`session-c.md:284` gives the path as `{src}events/{Event}.java`, and `session-d.md:39` reads it back
as `` (`{src}events/{Event}.java`) ``. Under the substitution the plan file lists are generated with,
those two resolve to `events/UpdateWarehouseName.java` — the suffix the plan row restores is dropped.
Either the session files should read `{Event}Event.java`, or they should say they use `{Event}` as
the full §4 name; as written the three files disagree.

**C2-4 (Major) — `classify-and-plan` Step 6.d tests an operation type its own parser never produces.**

Step 2.c (`SKILL.md:133-141`) fixes the vocabulary: "Kind (`Write` or `Read`; match
case-insensitively) … a missing or unrecognised `Kind` value is a malformed spec: halt". Step 6.d's

saga_states[agg] = ['IN_' + screaming_snake(f.name)

`create` is not a value `operation_type` can hold, so the filter is a no-op as written and the prose
above it ("Create functionalities contribute no constant") is unimplementable from the pseudo-code.
The prose is right and the code is wrong. Step 6.a additionally compares against bare `write` / `read`
(`SKILL.md:419,421`) rather than the `Write` / `Read` Step 2.c parses.
